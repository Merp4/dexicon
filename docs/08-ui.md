# 08 — UI

## Intent

Minimal but professional. The UI exists to answer four questions and to do nothing else:

1. What is indexed, and is it current?
2. What is the indexer doing right now, and did anything fail?
3. Does search return what I expect?
4. Who can see what?

Anything that does not serve one of those is not in v1.

## Stack

React 19 + Vite + Tailwind v4, built at image build time into `wwwroot` and served by the
same ASP.NET Core host. Dark and light, following `prefers-color-scheme` with a manual
override.

**Components are shadcn** (Radix primitives + `cva` + `cn`), living in
`src/components/ui` exactly as the shadcn CLI writes them, so `shadcn add` and
`shadcn diff` keep working. `src/ui.tsx` is the layer between that and Dexicon's own
vocabulary: `Modal`, `Field`, a `Badge` with a tone, a `Notice` with the same tones for
anything the screen has to say that is not an error, a `Chip` for "one of these is
current", a `Segmented` for one-of-N, a `Button` whose confirming variant is called
`primary`.

This replaced hand-rolled primitives. `.input` and `.btn-primary` were opt-in classes on
bare elements, and a whole modal shipped with every field rendering with no border and every
primary button identical to Cancel. Nothing threw, the types were fine, the build was clean
and 163 server tests passed; it was found by someone looking at a screenshot. A component
you cannot construct *without* its styling removes the class of mistake.

The palette is not duplicated. `index.css` maps shadcn's token names onto the oklch
tokens already defined, through `@theme inline`, so a generated component arrives
Dexicon-coloured in both modes. Note that shadcn's `accent` means "hover surface" while
Dexicon's `--accent` is the brand blue: the blue is `primary` here, and nothing redefines
`--accent`.

Each of the five meanings carries two values: `--warn` for the 12% fill and the 40%
border, `--warn-text` for the words on them. A single token cannot do both jobs. Tuned to
make a good fill, `--warn` as text measured 2.95:1 on the light surface and `--ok` 3.31:1,
against the 4.5:1 that 12px type needs, so every badge in the app failed in both themes.
The split moves only what is read.

Icons are `lucide-react`, on the navigation and on actions that are easy to confuse or
expensive to get wrong. Not on everything.

**The API client is generated** from the OpenAPI document by `@hey-api/openapi-ts`, from
the `Dexicon.json` that `dotnet build` writes, a file rather than a running instance, so the
client always matches the code it came from. `src/api.ts` is a thin facade over it.

Two things that facade must keep doing:

- **Attach the token itself.** The client's `auth` option is only consulted for
  operations the OpenAPI document marks as secured. The document declared no security
  scheme, so `auth` was never called, every request went out anonymous, and the UI
  reported the resulting 401 as a bad token. The document now declares the scheme *and*
  a request interceptor sets the header, because whether a request carries credentials
  should not depend on a generated file being right.
- **Read the response envelope.** `throwOnError: true` was configured but had no effect:
  the generated SDK still defaults to `ThrowOnError = false`, so a failure
  returns `{ data: undefined }`. Returning that `undefined` put it into component state
  and the next `.map` blanked the page. `call()` checks `error` and `response.ok` rather
  than trusting the flag.

## Tests

`vitest` + jsdom + Testing Library, `npm test`. They assert `data-slot` and `data-variant`
(the component library's own markers) rather than class lists, because "this is the
component, wearing the variant asked for" is the thing that broke and a class list is free
to change. jsdom computes no layout, so nothing here can tell you a field is *visible*;
that needs a real browser and is a slower, different kind of test.

## Shell

```
┌──────────────────────────────────────────────────────────────────────┐
│ Dexicon                                      ● qdrant ● ollama  ⚙︎  │
├────────────┬─────────────────────────────────────────────────────────┤
│ Search     │                                                         │
│ Corpora    │                                                         │
│ Documents  │                    ( active view )                      │
│ Jobs       │                                                         │
│ Models     │                                                         │
│ Access     │                                                         │
│ Settings   │                                                         │
└────────────┴─────────────────────────────────────────────────────────┘
```

**The screen is in the URL**, as a fragment: `#/corpora`, `#/corpora/books`, `#/settings`.
Reload, bookmark and the back button all work from it; before, a reload landed on Search
whatever you were reading, and the back button did nothing at all.

In the fragment rather than the path, because the app is served by the same origin as the
API and every path but `/` needs a token: a real path would 401 on exactly the reload this
fixes, and widening the anonymous list would trade a security surface for a prettier URL.
The browser never sends a fragment to the server.

Nothing else is kept there. A search query or a scroll position in the URL is a promise to
restore state that is not actually restored, and an unrecognised fragment lands on Search
and rewrites itself rather than showing a blank page.

The two status dots are live (SSE) and open a popover with the detail: each dependency's
endpoint and whether it answered, and the embedding provider by name, since which provider
is the default is configuration.

A dev tool that hides whether its dependencies are healthy wastes an hour of someone's day
per incident.

It does not show the default model or its dimensionality. Those are properties of a chunk
set, not of the deployment — each set records the model it was built with and keeps it,
and the dimensionality decides which Qdrant collection it lives in — and the corpus form
already shows the default at the one moment it applies.

What it shows instead is the inverse: a chunk set whose model the provider no longer has.
That set still says `ready` and its vectors are still in Qdrant, but no query for it can
be embedded, so it answers nothing and reports nothing. Both dots stay green, which is why
the collapsed button carries its own mark. The warning names the affected sets as
`corpus:set`, because the fix is per set: pull the model back, or build a set on a model
that exists and promote it.

Only providers whose models can be listed are checked, and an unreachable provider is not
reported as a missing model. A hosted catalogue is the configured list rather than what
the backend holds, and the embedding health beside it already says when a backend is down;
a warning that fires on a working deployment costs more than the one it catches.

## Views

### Search

The default landing view, because it is the thing you want to check.

- Query box, focused by `/`, searching on Enter; a segmented control for
  `hybrid | semantic | keyword`; a corpus picker, **All corpora** or one; a limit of 5, 10,
  20 or 50. The segmented control is a radio group, so it is one tab stop with the arrow keys
  moving between options rather than three separate stops. The API takes a list of corpora;
  the picker sends one or none.
- While a search runs, cards in the shape of the answer stand in for it and the previous
  result is hidden, because its header and passages would be a stale answer to the new query.
- Results as cards: the citation in monospace (`file_path:start-end`, or the document and its
  section, such as a page), language and corpus badges, the score, **Copy path** and
  **Open**. The corpus badge appears when more than one corpus was searched. The passage
  marks the query's terms as the keyword index reads them, whole and split at identifier
  boundaries, so a query for `RefreshAsync` also marks "refresh". It uses the index's term
  lengths and stopwords, and leaves common words such as "which" unmarked when the query has
  them as words of their own, since a word in nearly every passage says nothing about why
  this one matched. Prose is set in the body face and code in monospace. **Open** shows the
  file as indexed, reading on past the first window if the hit is further in, scrolled to
  the hit with the hit's lines marked.
- **Explain**, per search: the corpora the scope resolved to, the mode that ran, and how that
  mode scores: DBSF over the dense and sparse lists for hybrid, cosine similarity for
  semantic, an IDF-weighted term match for keyword. A score is comparable within one search,
  not across searches. This is how you tell "the index is bad" from "the scope was wrong",
  and it is the single most useful thing the UI can show.
- Degraded searches render a banner naming the reason, never an unannounced keyword-only
  result that looks like a hybrid one, and Explain names the mode that ran. A search that
  reached a corpus still indexing says its results are incomplete.

### Corpora

List: name, state, last indexed, description, files, chunks, pending, skipped and failed
counts where there are any, the default set's embedding model, the number of chunk sets
when there is more than one, and a progress bar while a job runs.

Detail:

- **Sources** — every folder this corpus reads, each showing what it is actually doing:
  whether `.gitignore` is honoured, the size cap, and any include/exclude globs. Add
  another with a picker that browses the mounted `/workspaces` tree, so you cannot name a
  path that is not there; it warns before indexing the same folder twice. It opens with no
  folder chosen, and the workspace root is a choice like any other, made with its
  breadcrumb. A file source there takes everything no deeper source claims, the loose files
  and every folder without a source of its own, so the dialog says so and its button reads
  **Add the workspace root**. A history source at the root is the repository's history and
  gets neither. Remove one and
  its files leave the index immediately, in every chunk set; the folder on disk is
  untouched, because Dexicon only ever reads it. With more than one source each row shows
  what it contributed, and a source that brought in nothing says so: that is what a
  mistyped path, an over-eager exclude glob and an index that stopped early all look like,
  and a corpus-level total hides all three. Owner-only, because writes always are.
  Documents arrive the other way, through the upload drop zone. Each workspace row opens an
  editor for its own filters, and **Default filters** sets what every source inherits. Filters
  used to be write-once: set when the folder was added and unreachable afterwards, so
  changing one meant deleting the source, which drops its files from every chunk set, and
  re-embedding the folder from scratch. A field the source does not set shows the corpus
  value it takes instead, named rather than implied, because a checkbox reading only "use
  the corpus default" asks someone to accept a value they cannot see. A row says
  `some from the corpus` only where a corpus default really reaches it: almost every source
  inherits the ABSENCE of globs, and a label on every row is one a reader learns to skip.

  A git-history row shows its ref, what each document holds, and the newest commit the
  last pass listed on that ref with its age (`newest 9d2ef06, 3d ago`, the full sha and
  date on hover), because a ref that stops moving is otherwise invisible: every count stays
  correct. Its editor holds the history settings rather than the file filters: the ref,
  message, stat, diff and its cap, merges, a commit limit and whether commits past it are
  kept once indexed, a date and the include paths. The keep checkbox appears only beside a
  limit and is cleared with it, since the server refuses it alone. Adding a history source
  shows the same fields, from one component, so the two cannot drift. A save sends every
  setting, because the server replaces the set. The editor says which kind of change it is
  about to make: the ref, the limit, the date and merges choose which commits are indexed
  and keep the documents already there, while the message, stat, diff and paths change
  what every document holds and re-read the history. Turning keeping off gets a warning of
  its own, because every held commit past the limit leaves on the refresh. Settings git
  cannot be asked with are refused by the server and shown in the dialog, which stays
  open. A source at the workspace root is named `workspace root`.

  What the source follows is picked, not typed, from `/api/workspaces/git`:
  **Checked-out branch** (`HEAD`), **A branch**, or **Other ref** for a tag or a commit.
  - **Checked-out branch** names the branch the checkout has out and how far it is behind
    its upstream as of the last fetch. When it is behind, **Follow origin/main instead**
    sets the upstream, because a local branch moves only when someone pulls: dexhistory
    sat 52 behind for three days with every count correct.
  - **A branch** is a list in three groups:
    - local branches, each with how far it is from its upstream;
    - remote-tracking branches, headed with when `git fetch` last ran;
    - refs prefetched by `git maintenance`, each with whether it points where the
      remote-tracking ref it copies does. Only the tips are compared, so "differs from"
      does not say which of the two is newer.

    A pick stores the full name (`refs/remotes/origin/main`), so a tag of the same name
    cannot take its place. A name the server refuses is listed, disabled, with the reason
    beside it. A source saved with a short name shows as picked, as the server resolved
    it, and is not rewritten until someone picks again. When git would walk a tag of that
    name instead, it shows under **Other ref** and says so.
  - **Other ref** is the text box it used to be, and is what shows when the branches
    cannot be listed, the folder is not a repository's root, or no folder is chosen yet.

  Changing the folder in the add dialog returns to the checked-out branch, because a branch
  belongs to the repository it was picked from. Dexicon does not fetch; the host does, and
  the page says when.

  The row says how current the ref was at the last pass. Following `HEAD`, it names the
  branch: `HEAD (main)`. A branch behind its upstream reads "52 behind origin/main as of
  the fetch 3d ago" in the warning colour; a branch that is only ahead says nothing. A
  remote-tracking ref reads "fetched 3d ago".
- **Files no source covers** — a `Notice` above the sources, naming the directory, up to
  five of the files in it and how many more. A file outside every source root is not
  skipped and not failed: it is absent, so it appears in none of the counts on this page,
  and a search for it returns other documents, which reads like a ranking result rather
  than a gap. Shown only where two or more of the corpus's sources share a parent
  directory, so a corpus that indexes one folder is not told it is missing everything
  beside it; `/api/corpora/{name}/coverage` decides that, and applies the same filters
  indexing would, so a reported file is one that would have been indexed. Its button opens
  the source picker already pointed at the directory, because a path read off a warning and
  retyped is where this goes wrong. For a gap at the workspace root that is the root itself,
  chosen. The root is the empty path, and the picker holds "nothing chosen" separately, so
  a form cannot mistake one for the other. Owner-only, like every other write.
- **Chunk sets** — directly under the summary, collapsed to one line by default. The line
  names the set an unqualified search reaches, with its model, dimensionality, size,
  overlap, chunk count and state, and badges any other set that is building, pending or
  failed, so nothing in progress is hidden. **Add set** stays in the header while it is
  collapsed. Whether it is open is remembered per browser under `dexicon.chunkSets.open`.
  It sat below the file list, which on a corpus showing 100 of 1,834 files was 5.8 screens
  down.

  Open, it lists every way this corpus is cut, each with its model, dimensionality,
  size and overlap, strategy flags, chunk count and pending count. The default is badged;
  each row shows the `corpus:set` name it answers to, with a copy button.

  **Add set** opens an editor that starts from the default set's settings. The size and
  overlap then follow the chosen model's measured suggestion, where **Test limits** on
  Models has measured it, until a size is typed; a model never measured keeps the inherited
  values. **Promote** asks first, naming the set search moves to and the one it leaves with
  both models, because it changes what every search of the corpus returns, agents' included.
  It is disabled while a set still has pending files, with the count in its tooltip. It is
  disabled rather than hidden so that the reason remains visible. Promoting a partially
  built set is the failure that building it separately exists to prevent.

  A set's model is fixed once it exists, and the editor says so: a different model is a
  different vector space, so it is a new set and a promotion, not an edit.
- **Files** — paged a hundred at a time, filterable by status and by name, sortable by
  name, size, chunk count or status. All four are the SERVER's: the list was filtered and
  ordered in the browser, which can only see the rows it fetched, so on a corpus larger
  than a page a file that exists read as one that does not. `skipped` and `failed` rows show
  `status_detail` inline. This is where "why isn't my PDF searchable" gets answered:
  *no text layer: this is a scanned PDF, and OCR is not supported*. A row opens the file
  as it was extracted, numbered by its real line numbers: what was *indexed* rather than
  what is on disk, because that is what search reads, and because an uploaded PDF has no
  file to open instead. A code file on a mount has no stored text, so that one is still
  stitched back together from its chunks, and gaps in the index are announced rather than
  closed silently. A search hit opens the same viewer at the hit, with its lines marked.

  A book is bigger than one response, so the viewer reads a **window** and offers **Read
  on**, which appends the next one. A 700-page technical book runs past two million
  characters. It reports the percentage on screen rather than a bare "truncated" badge,
  and the line numbers in the header are the window's own: the earlier version showed the
  whole file's range over a fraction of its text, so every number past the first screen
  was wrong.
- **Actions** — Refresh, Full reindex, Delete.

  **Refresh** queues an incremental pass and runs on the click: it embeds what moved, which
  on an unchanged tree with nothing failed is nothing at all. A failed file has no
  fingerprint to skip on, so a refresh retries it.

  **Full reindex** asks first. It reads every item again whether or not it changed, and
  re-embeds the ones that can be read and chunked, in every chunk set — one that is
  excluded, oversize or empty is recorded without being embedded, as on any pass. It sat
  one click from Refresh with nothing between two actions that are not comparable. The
  dialog carries the size of the thing, summed across sets because the job names none and
  the indexer runs each, and each set's model, size and overlap, which are set under Chunk
  sets and were otherwise nowhere near the button.

  The chunk figure is **what the catalogue holds now**, and is worded that way. There is no
  planned count to ask the API for: a pending row has no chunks yet, a failed one keeps the
  count it last had, and a file that changed will produce a different number this time.

  Files are named **per set** rather than totalled. `fileCount` on the corpus is the
  default set's, deliberately, because that is what an unqualified search reaches — and a
  file held in two sets is still one file, so a sum would be neither. Chunks do total
  honestly: a chunk belongs to exactly one set. The failure count is per set and per item
  too, so with more than one set it is reported as failures rather than as documents.

  The unit follows the corpus, through the same `unitFor` the rest of the screen uses: a
  git-history corpus fails commits, a mixed one fails documents.

  It does not ask for the corpus name, unlike Delete. The corpus is not cleared up front —
  vectors are replaced one item at a time as the walk reaches it — so the rest of it stays
  searchable throughout. The item in hand does not: its old vectors are deleted before the
  new ones are written, so it is missing for that moment, and stays missing until a later
  pass if its embedding fails or the job is interrupted. The question is cost, and a
  window on one item at a time, rather than damage.

  The dialog carries the two things people reach for this button wanting, because it is
  neither of them: a **different embedding model** needs a new chunk set, and **new or
  changed files** need Refresh, which the dialog offers directly so that finding out here
  does not mean cancelling and going looking. Its link to Chunk sets closes the dialog and
  opens that section. Where a set has failures it says so, and says a refresh retries them
  too — a failed file has no fingerprint to skip on. The dialog opens with focus on
  **Cancel**.

  **Delete** requires typing the corpus name; it destroys an index that may have taken an
  hour to build. The chunk count it gives is every set's, since all of them go.

Creating a corpus is one dialog: name, embedding model (with the trade-off table from
[04](04-ingestion.md) inline), first source. Everything else has a working default, and
the corpus is born with one chunk set named `default` carrying it.

### Jobs

Current job with a progress bar, phase, current file, counts (`done / skipped / failed`),
and a derived time estimate. History below, newest first, each expandable to its per-file
failures.

`degraded` is a first-class state with its own colour, distinct from both running and
failed, showing the backoff count and next retry. A job that is technically running but
achieving nothing must not look like a job that is working.

**The list is runs that did something**, requested as `GET /api/jobs?activity=true`.
`DEXICON__INDEXING__REFRESHMINUTES` enqueues one refresh per corpus per interval and on an
unchanged tree every one of them succeeds having indexed nothing, so the filter belongs in
the query: a client can only collapse what it was sent. Measured on a live instance at ten
minutes and five corpora, the last 200 jobs spanned 449 minutes, 48 of them did real work,
and not one of those 48 was in the most recent thirty — so a page of thirty was an hour of
silence covering everything worth reading. "Show routine refreshes" asks for the lot and
collapses consecutive quiet runs into one line, which is what the whole list used to be.

A failed or degraded run has the same zero counters as a quiet one, so the filter is
"not succeeded, **or** it indexed something, **or** it wrote chunks" rather than a test on
the counts alone.

**It polls every 30 seconds, and every 4 while something is running.** The progress stream
already pushes a live job's counters, so the poll only has to notice a run starting or
ending — and the stream notices the start first, which re-arms the fast interval on the
same tick. It polled every 4 seconds for as long as the tab was open, whatever was
happening.

### What the stream actually sends

`/api/events` serialises `IndexProgress`, and the client typed it as a `JobSummary`. The
two differ in exactly the fields a reader reaches for first, so the compiler agreed with
code that could never work:

| | `JobSummary` | `IndexProgress` |
|---|---|---|
| identity | `id` | `jobId` |
| state | `state` | — |
| stage | `phase`, null when done | `phase`, the STATE NAME when done |

The server sends `job.Phase ?? job.State.ToString()` after nulling `Phase`, so the last
event of a run carries `"Succeeded"` rather than nothing. Three things were quietly dead
as a result: the jobs list matched `live[...]?.id === j.id` and never merged a live
event, the corpus detail reloaded when `phase` went absent and so never reloaded, and the
corpus list refreshed on `p.state` and so never refreshed.

`live` now holds one shape — `Progress` — with the jobs listing mapped into it when
seeding, and `isRunning` is the single test for "still going", which is *the phase does
not name a terminal state* rather than *the phase is absent*.

### Access

API keys: list, create, revoke, and for each one the corpora it reaches. Nothing ticked
reads as "every corpus", because that is what it means, and the way to stop a key reaching
anything is to revoke it. Changing the ticks takes effect on that agent's next call;
granting `ingest` is listed to it when its client next reconnects, and the page says so,
because a silent difference between the two reads as a defect.

Key creation shows the secret **once**, in a dialog with a copy button and a plain
warning that it will not be shown again, alongside a ready-to-paste command:

```bash
claude mcp add --transport http dexicon http://localhost:8477/mcp \
  --header "Authorization: Bearer dex_..."
```

That snippet is the step between "installed" and "working".

Token list: name, each scope, last used, an expired or revoked badge, the corpora it
reaches, and **Revoke**. Never the secret. Revoke asks first: whatever holds the key is
refused on its next call, and nothing on the page restores it.

### Models

What this Dexicon's Ollama has pulled, so choosing a model is a list rather than a typing
exercise. A typo otherwise surfaces as a 503 at corpus creation, with no hint of what the
legal values were.

Providers run along the top when more than one is configured. One that is configured but
missing its credential is marked, with the reason; otherwise it appears identical to a
working one until someone picks it and an index fails an hour later.

Each row: name, size, dimensionality where known, and whether a chunk set uses it.

**Test limits** measures what the model accepts (dimensions, the real input limit, and
whether it truncates without erroring) and suggests a chunk size with headroom. It embeds
throwaway filler and indexes nothing. Truncation is otherwise undetectable: a truncating
model returns a perfectly good vector for the part it read.

**Pull** takes a model name and streams progress, since a pull is gigabytes and minutes. It
appears only for providers whose models are local; you cannot pull a model into OpenAI.

**Delete** is refused while any chunk set embeds with the model, and while it is the
configured default for new corpora; the reason names the sets rather than making you find
out by trying.

Names are compared with `:latest` normalised away: Ollama reports
`nomic-embed-text:latest` and a chunk set records `nomic-embed-text`.

Only embedding models are listed. Ollama serves chat models from the same endpoint and
they cannot embed, so offering them would turn a bad pick into a 503 at index time. The
filter is a name heuristic and is labelled as one; the real check still runs when a model
is chosen.

### Settings

Deployment-wide: default embedding model and chunk settings for *new* corpora, refresh
interval, concurrency limits, upload size caps, Qdrant and Ollama endpoints (read-only,
showing what the environment supplied). A **Check connectivity** button that calls both and
reports what it found.

## Live updates

One SSE stream, `GET /api/events`, multiplexing job progress, health changes, and corpus
state. Reconnects with backoff, and shows a "reconnecting" indicator rather than
freezing without explanation. Events are scoped to what the caller can reach.

Polling fallback if SSE fails twice, at 5 s, with the UI saying it has fallen back.

## Accessibility and polish

Keyboard-first: `/` focuses search, `Ctrl/Cmd+K` opens the corpus switcher, `Esc` closes.
Visible focus rings, labelled controls, dialogs that trap focus and restore it. Empty
states that say what to do next rather than "No data". Errors that quote the server's
message instead of "Something went wrong".

Every confirmation is a `Modal`. `window.confirm` paints a dialog the page has no say
over: it ignores the theme, places the destructive action wherever the browser likes, and
after the second one a browser offers to suppress further dialogs for the session, at
which point a destructive action stops asking.

Progress bars carry `role="progressbar"` and their caption as `aria-valuetext`, and a
`Notice` is a live region, so a search running against a half-built index is announced
rather than only coloured. Text meets 4.5:1 against its own background in both themes;
the sweep that checks it walks every view and resolves the oklch tokens to measure them.

Every view names itself in an `h1` at one size, with sections as `h2` at one size below
it. Search's is `sr-only`: the screen needs a name in the outline, and a "Search" title
over a search box does not earn its place on the one screen you look at most.

`color-scheme` follows the chosen theme rather than the operating system. The tokens only
colour what this stylesheet draws; scrollbars, the caret, the reveal button in the token
field and autofill are the browser's, and it picks those from `color-scheme`. Left unset,
an OS on light and an app on dark produced pale scrollbars down every code block.

Motion is short and only on arrival: dialogs and the health popover fade and scale from
the control that opened them, banners fade in, progress bars ease their width. Nothing
animates on a route change. `prefers-reduced-motion` collapses every duration to
near-zero rather than removing the animation, because an exit animation that never runs
leaves a dismissed dialog on screen.

A dialog shows its own failures, at its top in the server's words, and stays open. The
page's error banner sits under an open dialog's overlay, and Radix marks everything
outside the dialog `aria-hidden`, so a failure sent there left the dialog open with
nothing in it to say why: measured with New corpus and a name already taken. A viewer
whose load fails says so instead of reading for ever. `DialogErrors.test.ts` holds every
`…Modal` and the file viewer to it by reading the source, so a new dialog is covered
without anyone writing a test for it.

## Not in v1

Bulk operations across corpora; a file browser for indexed content; saved searches; charts
of index growth; a settings page for every option in `appsettings.json`. Each is a
reasonable idea and none of them answers one of the four questions at the top.
